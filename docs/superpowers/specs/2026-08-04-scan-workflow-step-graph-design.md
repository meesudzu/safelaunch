# Scan Workflow Step Graph — Refactor for Visualizability + Durability

## 1. Background

The `scan-workflow` Worker is the orchestration that turns an inbound `POST /v1/scans`
request into a compliance verdict (`high_risk` / `needs_review` / `no_significant_risk`)
together with a reportable artifact.

In the Cloudflare dashboard, every workflow instance now shows a banner:

> The latest instance of this workflow doesn't have a graph yet. Deploy a new version
> to automatically generate a workflow graph.

Reading `apps/workers/src/workflows/scan-workflow.ts:327-352`, the implementation
**literally ignores the `step` parameter**:

```ts
export class ScanWorkflowEntrypoint extends WorkflowEntrypoint<...> {
  async run(
    event: Readonly<WorkflowEvent<ScanWorkflowPayload>>,
    _step: WorkflowStep,   // ← underscore = discarded
  ): Promise<ScanResult> {
    return runScan(params, { fetch, evaluate, persistReport, persistTerminalState, ... });
  }
}
```

Cloudflare's durable-execution graph visualizer is generated by **static analysis of
`step.do()` / `step.sleep()` / `step.sleepUntil()` / `step.waitForEvent()` call sites**
inside `run()`. With zero such calls, the graph is empty — even though the workflow
itself still runs because the engine executes `run()` as one unit-of-work.

Beyond the visualization gap, the current shape also **discards most of the durability
guarantees the engine offers**:

- Every fetch, AI evaluation, and DB write is replayed on any failure
  (because the whole `runScan` body is one unit).
- AI evaluation is non-deterministic and expensive; replaying it on a transient
  fetch failure is wasteful.
- No granular observability: when a scan fails, you only see a single "workflow failed"
  log line, not the failing phase.

## 2. Goals (in scope)

- `G1` Cloudflare dashboard shows a populated workflow **Graph** for `scan-workflow`,
  with each major phase as a distinct node.
- `G2` Each phase is an **independently retryable** `step.do()` boundary, so a
  transient failure in phase N retries only phase N (not phases 1..N-1).
- `G3` All writes triggered by `step.do()` are **idempotent**: a replay does not
  create duplicate rows, duplicate tokens, or duplicate log entries of business
  significance.
- `G4` The existing unit-test suite (`scan-workflow.test.ts`, which drives `runScan`
  directly via dependency injection) **keeps passing without modification**.
- `G5` Multi-jurisdiction / multi-category behavior is preserved (no scoring change).
- `G6` No new PII enters logs (compliance-skill rule).
- `G7` AI-evaluation phase remains a single `step.do()` (not split per-rule)
  to keep AI cost predictable.

## 3. Non-goals (out of scope)

- `N1` Changing scoring rubric or compliance logic (`packages/compliance-core`).
- `N2` Changing AI prompts or retrieval (`packages/ai`).
- `N3` Splitting AI evaluation per-rule (would multiply provider cost per retry).
- `N4` Adding `step.sleep()` for rate limiting between AI calls (deferred —
  see Future Work).
- `N5` Renaming the workflow entrypoint class or its D1 binding name
  (`SCAN_WORKFLOW`). External callers consume a Workflow binding; renaming is a
  breaking change.

## 4. Granularity decision (assumption)

This spec assumes **medium granularity**:

| Phase                      | Granularity                                               |
| -------------------------- | --------------------------------------------------------- |
| Bootstrap                  | one `step.do("parse-params", ...)`                        |
| Page fetch                 | one `step.do("fetch:${pageType}", ...)` **per page type** |
| Evidence extraction        | one `step.do("extract-evidence", ...)` (pure post-fetch)  |
| Rule evaluation (AI)       | one `step.do("evaluate-rules", ...)` (entire fan-out)     |
| Aggregation                | one `step.do("aggregate-findings", ...)`                  |
| Report persistence         | one `step.do("persist-report", ...)`                      |
| Terminal-state persistence | one `step.do("persist-terminal", ...)`                    |

That yields ~8–12 nodes depending on `requirePages`, **single AI-evaluation node**.
Trade-off vs. fine-grained (per-rule): AI cost does not multiply on retries and graph
remains readable. Trade-off vs. coarse: any fetch failure retries only the
failing page rather than the entire fetch loop.

If the user wants a different granularity, this is the only section to revise.

## 5. Architecture

### 5.1 New file layout

```
apps/workers/src/workflows/
├── scan-workflow.ts                  # entrypoint + orchestrator + runScan (compat shim)
├── scan-workflow.phases.ts           # NEW: pure per-phase helpers (testable)
└── scan-workflow.phases.test.ts      # NEW: unit tests for each phase
```

`runScan` stays as the entry-point-injected orchestrator (it accepts `deps` for
DI). Internally it will be restructured to delegate to phase helpers in
`scan-workflow.phases.ts`, but its **public signature, return type, and overall
flow stay identical** so `scan-workflow.test.ts` keeps passing.

### 5.2 Step map (graph view)

```
                  ┌────────────────┐
                  │ parse-params   │
                  └────────┬───────┘
       ┌──────────────┬─────┴──────┬──────────────┐
       ▼              ▼            ▼              ▼
  fetch:homepage  fetch:about  fetch:privacy  fetch:contact
       │              │            │              │
       └──────┬───────┴────────────┴──────────────┘
              ▼
       extract-evidence
              ▼
       evaluate-rules   ← single node, retries rerun the whole AI fan-out
              ▼
       aggregate-findings
       ┌──────┴───────┐
       ▼              ▼
  persist-report  persist-terminal
```

If homepage fetch fails, we **short-circuit** to `persist-terminal(state=failed)`
and return — no further nodes, mirror of the current early-return behavior.

### 5.3 Step type matrix

| Step name            | Idempotency strategy                                           | Side effects                      |
| -------------------- | -------------------------------------------------------------- | --------------------------------- |
| `parse-params`       | pure function, no side effects                                 | none                              |
| `fetch:${page}`      | pure retry; HTTP GET is naturally re-runnable                  | none (raw HTML not yet persisted) |
| `extract-evidence`   | pure on input `pages[]`                                        | none                              |
| `evaluate-rules`     | AI call is naturally re-runnable; cached retrieval is OK       | none                              |
| `aggregate-findings` | pure                                                           | none                              |
| `persist-report`     | DB upsert on `scan_id`, **deterministic token** (see §5.4)     | `ReportRepository.upsert`         |
| `persist-terminal`   | DB update is idempotent on `scan_id`, idempotent state machine | `ScanRepository.updateTerminal`   |

Every step that writes to the DB **must** be idempotent because Cloudflare replays
the entire `step.do()` body if the function throws or the workflow is restored.

### 5.4 Deterministic report token

Today the token is `crypto.getRandomValues(24 bytes)` then `rpt_${hex}` (**non-deterministic**).
If `persist-report` retries, we mint a new token, the report URL changes, and any
caller holding the old URL breaks.

Fix: derive a **deterministic token** from inputs that cannot change across retries:

```
token = "rpt_" + sha256hex(scanId)
tokenHash = sha256hex(token)        // still random-looking externally
```

A deterministic token survives retries: a replay produces the same token, the
upsert replaces the same row, and the public URL stays stable.

`R2 ARTIFACTS` (raw HTML) is **not** affected by this refactor — uploads are still
performed outside the workflow by `apps/workers/src/routes/scans.ts`, not by the
workflow itself.

### 5.5 StepConfig (retry policy)

All `step.do()` calls use Cloudflare's default retry policy except `persist-report`
and `persist-terminal`, which use:

```ts
{
  retries: { limit: 5, delay: "2 seconds", backoff: "exponential" },
  timeout: "30 seconds",
}
```

Rationale: DB writes occasionally see D1 contention; 5 retries with exponential
backoff is enough to absorb cold-start latency without making instance runtime
degenerate. Fetch and AI steps keep Cloudflare's default retry policy.

(Note: read the actual `WorkflowStepConfig` type from
`@cloudflare/workers-types` when implementing — names above are from the Cloudflare
docs and may shift across versions. Pin the wrangler / `workers-types` version
when this lands.)

## 7. Compliance considerations

- **No PII** in step names (they become log labels). Names are public-safe enums
  like `fetch:privacy`, `evaluate-rules`.
- **Citation flow is unchanged.** Aggregation produces the same `ReportFinding`
  array with the same `citations[]` shape.
- **Deterministic token** does not weaken security: the token is still 32 hex
  chars of SHA-256 entropy from the scan id (UUID v4 in practice), still
  effectively unguessable. The `expiresAt` 7-day window still applies.
- **Rubric version unchanged.** `RUBRIC_VERSION` constant at the top of
  `compliance-core` is read as-is.

## 8. Risk register

| Risk                                                        | Likelihood | Impact | Mitigation                                                             |
| ----------------------------------------------------------- | ---------- | ------ | ---------------------------------------------------------------------- |
| AI-evaluation step is expensive on retry                    | medium     | medium | Cap retries to 2 (default Cloudflare limit is higher). Document cost.  |
| Refactor breaks existing test suite                         | low        | high   | Run full test suite in CI before deploy. Pin test fixture.             |
| Step names appear in Observability logs with PII concerns   | low        | low    | Names are public enum strings; reviewed per §7.                        |
| Dashboard doesn't render graph even after deploy            | low        | medium | Open a real instance, wait 5 minutes, check the Graph tab. Re-trigger. |
| Workflow binding name change accidentally regresses in prod | low        | high   | Wrangler binding name is `SCAN_WORKFLOW` — confirmed unchanged.        |

## 9. Migration / rollout plan

Three stages, sequentially:

### Stage 1 — Local + CI (no deploy)

- Implement `scan-workflow.phases.ts` and unit tests.
- Restructure `scan-workflow.ts`. Add `step.do()` wrappers.
- `pnpm -w test`, `pnpm -w typecheck`, `pnpm -w lint` all pass.
- `pnpm -w --filter @safelaunch/workers wrangler deploy --dry-run` succeeds
  (proves the Worker bundles, no runtime check).

### Stage 2 — Staging env (preview deploy)

- Deploy to a preview Worker (`wrangler deploy --env staging` or the
  team's preview alias — confirm with user).
- Trigger one real `POST /v1/scans` via staging API.
- Confirm the workflow instance in the dashboard shows a populated Graph
  with all expected step nodes and that the verdict is identical to current
  behavior.

### Stage 3 — Prod

- Deploy to prod via the team's normal release process.
- Watch one full scan in prod dashboard, confirm graph renders.
- Roll forward; ready for code review + merge.

If any stage fails, stop. Do not proceed. Surface the failure to the user.

## 10. Open questions for the user

Please confirm or override before we move to the implementation plan:

- `Q1` Granularity = medium (per-page + per-phase). OK or change to fine/coarse?
- `Q2` Report token: switch to **deterministic** (`sha256(scanId)`-based)?
  - Pro: replay-stable URL.
  - Con: token leaks scanId-prefix to anyone who guesses; mitigated by the
    32-char hex output space.
- `Q3` Staging env name (so I can correctly target the deploy command).
- `Q4` Is `persist-terminal` always last, even on partial/failed state?
  Currently `runScan` calls it after a successful fetch of homepage AND after
  the evaluate+persist branch. The new design needs the same dual call paths
  wired.

## 11. Future work (not part of this spec)
