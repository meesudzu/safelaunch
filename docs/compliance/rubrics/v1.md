# Compliance Rubric v1 — `vn-mvp-v1`

> This document is the binding spec for every RuleResult emitted by
> `@safelaunch/compliance-core`. The rubric hash (`RUBRIC_VERSION`) is
> included in every result and recorded in `analysis_runs` so that historical
> findings can be reproduced and audited.

## Scope

| Field            | Value                                                      |
| ---------------- | ---------------------------------------------------------- |
| Jurisdiction     | `VN` (Vietnam)                                             |
| Categories       | `online_game`, `electronic_press`, `digital_entertainment`  |
| Report locales   | `vi` (default), `en`                                       |
| Source hosts     | `vbpl.vn`                                                  |
| Rubric version   | `vn-mvp-v1`                                                |
| Severity scale   | `pass`, `review`, `high`                                   |
| Outcome scale    | `present`, `absent`, `unknown`                             |
| Status scale     | `no_significant_risk`, `needs_review`, `high_risk`         |

## Severity model

`severityFor(outcome)` is the only authority on severity:

| Outcome   | Severity | Aggregate impact |
| --------- | -------- | ---------------- |
| `present` | `pass`   | none             |
| `unknown` | `review` | expert review    |
| `absent`  | `high`   | blocks launch    |

A scan's overall status is derived from the highest severity among its rule
results:

- any `high` ⇒ `high_risk`
- otherwise any `review` ⇒ `needs_review`
- otherwise ⇒ `no_significant_risk`

A technical failure (failed page fetch) MUST NOT silently downgrade to
`no_significant_risk`; coverage-aware rules return `unknown` and the workflow
forces the scan status to `needs_review`.

## Reproducibility contract

For identical inputs (same `scanId`, `jurisdiction`, `category`, `coverage`,
`evidence`) the `runRules` function returns a deeply-equal `RuleResult[]`
including the embedded `rubricVersion`. There are no timestamps, random
seeds, or environment-derived values in the output.

## Rule registry

Each entry documents: rule ID, applicable categories, evidence types that
flip the rule to `present`, the pages whose failure forces `unknown`, the
citation it carries when `present` or `absent`, and the rationale templates
(English / Vietnamese).

## Output contract

```ts
interface RuleResult {
  ruleId: string;            // stable identifier; see registry above
  title: string;             // short Vietnamese headline
  outcome: "present" | "absent" | "unknown";
  severity: "high" | "review" | "pass";
  rationale: string;         // non-empty, human-readable
  evidenceIds: string[];     // empty when outcome is "absent"
  citations: Array<{ provisionId: string; source: string; excerpt: string }>;
  rubricVersion: "vn-mvp-v1";
  applicability: "current";  // upcoming rules will introduce "upcoming"
  categories: AppCategory[]; // which scan categories this rule applies to
}
```

## Coverage semantics

For a rule with required pages `[p1, p2, …]`:

| Page state                                     | Outcome     |
| ---------------------------------------------- | ----------- |
| Any required page has matching evidence         | `present`   |
| All required pages failed                       | `unknown`   |
| Any required page failed AND none fetched       | `unknown`   |
| All required pages fetched, no matching evidence | `absent`    |

The verifier (Task 13) MUST reject any `RuleResult` whose outcome is
`present` or `absent` but whose `evidenceIds` is empty.

## Anti-pattern guard

The rules engine never:

- Hard-codes a numeric score (severity is the only scoring signal).
- Uses the website URL or excerpt inside the rationale.
- Treats an `absent` outcome as `pass` (absent failures are escalated).
- Reads PII beyond what is necessary to identify the page (no clipboard scraping, no third-party calls).
